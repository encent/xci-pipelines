# XCI pipeline

Reproduces the chromatin-analysis figures from our Nature Genetics paper on
X-chromosome inactivation: what keeps "escapee" genes active on the inactive X, and
whether CTCF or cohesin maintains that state.

Starting from allele-split BAM files and Capture Hi-C contact maps, it produces every
panel of **Fig 2g,h · Fig 3 · Fig 4d,e,f,g · Fig 5b,c,g,h · Fig 6 · EFig 2e,f,g ·
EFig 3 · EFig 6a,b,c · EFig 8c,d · EFig 10c,d**, plus a table of every number quoted in
the paper.

---

## Three commands

```bash
bash install.sh          # once, ~20 min, needs internet
bash configure.sh        # tell it where your data is
./run.sh                 # go
```

Then open `results/REPORT.html` in a browser.

**Before you commit to the real thing, do this:**

```bash
./run.sh demo            # ~2 hours, small, proves your setup works
```

### How long the real run takes

**About 2–3 days on a 48-core desktop, writing roughly 500 GB.** That is not a typo —
the input is ~760 GB of BAM files and the dominant cost is generating ~250 coverage
tracks from them. The run is resumable: if it stops, `./run.sh` again picks up where it
left off and recomputes nothing.

If you only want one figure, say so and the pipeline computes only what that figure
needs:

```bash
./run.sh panel Fig3a
```

## What you need

| | |
|---|---|
| OS | Linux (this is what we tested; macOS may work, Windows will not) |
| Cores | 8 minimum, 48 assumed for the timings above |
| Memory | 32 GB minimum, 64 GB comfortable |
| Disk | ~600 GB free for a full run |
| Software | [conda / Miniforge](https://github.com/conda-forge/miniforge) — everything else is installed for you. `install.sh` resolves packages with mamba (bundled with Miniforge, and bootstrapped automatically if absent) because conda's own solver can take 40+ minutes on this environment. |

## What to edit

One file: `config/config.yaml`. Only the blocks marked `[EDIT ME]` matter.

| block | what it is |
|---|---|
| `paths.inputs` | where your BAMs and Hi-C coolers live. **The pipeline never writes here** — it only makes symbolic links. |
| `paths.data_dir` | where the pipeline writes. Needs ~600 GB. |
| `genome` | leave every value as `auto` and the mm10 reference downloads itself. |
| `loci` | the two chrX regions. Leave alone to reproduce the paper. |
| `figures.panels` | `all`, `paper` (just the 25 published panels), or a list like `[Fig3a, Fig6]`. |

`bash configure.sh` opens this file and then checks it, so you find out about a typo in
one second rather than one day.

## What you get

```
results/
├── REPORT.html            every figure on one page. Start here.
├── figures/               the panels, as SVG and PDF
├── figure_manifest.tsv    which file is which paper panel
├── paper_numbers.tsv      every number quoted in the paper, with its source
├── tables/                the data behind each figure
└── provenance.json        exact software versions, config and git commit
```

**The pipeline stops at panel-level SVG and PDF.** It does not assemble multi-panel
figures — that was done by hand in Illustrator, and claiming otherwise would be false.
The SVGs are editable, with text kept as text, so you can assemble them yourself.

## If something goes wrong

The error message tells you what happened and what to type. If it does not,
that is a bug in the pipeline and we would like to know.

* `docs/TROUBLESHOOTING.md` — the common cases
* `results/../logs/` — one log per step
* Nothing is lost on a failure. `./run.sh` resumes.

## Notes for the careful reader

**One environment, three underneath.** You create and activate `xci-pipeline`. The
pipeline silently manages two more, for METALoci and coolbox, because those tools pin
mutually incompatible Python versions — `cooltools 0.5.4` requires Python 3.9 and
`metaloci 1.3.2` requires 3.11. We kept the versions that produced the paper rather than
upgrading to make the packaging tidier.

**Normalisation is computed on autosomes only.** The library-size factors deliberately
exclude chrX: one X is inactivated, and *which* parental X differs between clones, so
including it would make the factors reflect X-inactivation instead of library size. The
pipeline refuses to start if you add chrX to that set.

**Two known quirks are reproduced on purpose**, because the published figures contain
them: a ~3.3 Mb "valley" at the start of chrX that is really the mm10 assembly gap, and
a scale-factor mis-assignment affecting five WT H3K27ac tracks. The second is *fixed* by
default; `legacy.h3k27ac_positional_scalefactors: true` reproduces the original exactly
for comparison. Both are documented in `the verification notes`.
